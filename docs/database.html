Database & Outbox

Migration system, schema reference, and the transactional outbox pattern.

Migration system

Migrations are plain SQL files embedded as assembly resources inside the Portfolio.TradeOrderService.Database project. The MigrationRunner runs automatically on API startup.

1

Create __migrations table (if not exists)

Tracks which migrations have already been applied. Created with IF NOT EXISTS so it's safe to run repeatedly.

2

Load embedded SQL files via reflection

Uses Assembly.GetManifestResourceNames() to find all .sql files, sorted by filename so they run in numbered order.

3

Compare against applied list

Any file whose name already appears in __migrations is skipped. Only new migrations run.

4

Apply in a transaction, record in __migrations

Each migration runs in its own transaction. On success the filename is inserted into __migrations. On failure the transaction rolls back and the app exits.

Adding a new migration: Create a new numbered SQL file (e.g. 005_add_filled_at.sql) in the Migrations folder, rebuild the image with docker compose up --build, and the runner applies it automatically on the next startup. Never edit existing migration files.

Migration files

  • 001create_orders.sqlorders table, indexes on account_id, symbol, status, created_at
  • 002create_outbox.sqloutbox table, indexes on status and created_at (partial — PENDING only)
  • 003create_ingestion_jobs.sqlingestion_jobs table for tracking data pipeline runs
  • 004create_audit_log.sqlaudit_log table for MCP tool call recording

Verifying applied migrations

docker exec -it portfolio-postgres psql -U admin -d tradeorders \
  -c "SELECT name, applied_at FROM __migrations ORDER BY applied_at;"

Outbox pattern

The outbox pattern ensures an order is never saved without a corresponding event and an event is never lost even if RabbitMQ is down.

Step 1 — Atomic write (single DB transaction)

POST /v1/orders →
Transaction INSERT INTO orders INSERT INTO outbox (status=PENDING)
→ commit

Step 2 — Relay (Sync background service, task #9)

SELECT … WHERE status='PENDING' → Publish to RabbitMQ → UPDATE outbox SET status='SENT'
On publish failure: status stays PENDING, attempts++ → retried on next poll
Why this matters: If RabbitMQ is unavailable when an order is created, the event sits safely in the outbox as PENDING. When RabbitMQ comes back, the relay catches up automatically — no events are dropped, no manual intervention needed.
